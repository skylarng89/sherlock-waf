# ADR-0018: API protection: OpenAPI engine, JWT verifier, JWKS, mutual TLS

- Status: Accepted (M9)
- Date: 2026-10-29
- Deciders: owner (plan approved; dependency choice approved)

## Context

M9 adds first-class protection for JSON and open-banking style APIs: conformance with an OpenAPI document, bearer-token validation, client certificates, and rate limits keyed on the caller's identity. The request path must make no network call (CLAUDE.md), validation must add at most 1 ms p95 (acceptance 1), and every URL an operator configures is an SSRF vector (threat T13).

## Decision

1. **OpenAPI engine: `kin-openapi`, no additional direct dependency.** The milestone proposed `kin-openapi` or `libopenapi` plus `santhosh-tekuri/jsonschema`. `kin-openapi` is already a dependency, parses 3.0 and 3.1, routes requests (its `routers/legacy`; `gorillamux` would add a dependency) and, for 3.1 documents, validates with JSON Schema 2020-12 through `santhosh-tekuri/jsonschema`, which it already imports. Using it avoids a second parser and a second router, and keeps one error model for parameters and bodies. A typical payment is checked in about 15 µs (`BenchmarkCheckTypicalPayment`), well inside the budget.
2. **Documents are untrusted input.** External references are never followed (no file or network reads at upload or at runtime), size is capped at 4 MiB, the document must validate and describe at least one path, and only 3.0.x/3.1.x are accepted. Server URLs are reduced to their base path, because the WAF sits behind whatever host the site serves. A document is compiled when it is uploaded and published through a copy-on-write registry; a replacement that fails to compile leaves the running document untouched. Violation messages are the schema error `Reason`, never the offending value, so account numbers and tokens do not reach events.
3. **Bodies.** The body is buffered up to `max_body_bytes` (default 1 MiB), validated and restored for the upstream. A larger or unbounded body is forwarded untouched, not validated, and an `api.body_not_validated` notice says so. Operators who need strictness lower the WAF body limit as well.
4. **JWT verifier is hand-written on the standard library.** The verifier is small, security-critical and must be fuzzed; a general JOSE library brings algorithm negotiation we do not want. Rules: the algorithm allow-list is RS256/384/512, PS256/384/512, ES256/384/512 and EdDSA (`none` and unknown algorithms are refused before anything else); HS256/384/512 are accepted only when the rule has a static secret, and an HS token is only ever verified against secret keys, never against a public key (algorithm confusion); the key type and curve must fit the algorithm; `crit` headers are refused; tokens over 8 KiB are refused; `exp` is required; `nbf`, `iss` and `aud` are checked when configured, with a bounded clock skew. A rule must set an issuer or audiences. The token is left in the request for the upstream.
5. **JWKS is fetched in the background.** One fetcher per URL is shared by every handler and reload (reference counted). It uses `internal/netx` (no loopback, private, link-local or metadata address after DNS resolution, no environment proxy, size cap, bounded redirects) and the URL must be https without credentials; literal internal addresses and `localhost` are also refused when the configuration is validated. Failed refreshes keep the previous keys. A token with an unknown `kid` requests an early refetch (at most one per 30 s), so key rotation needs no restart and no request ever waits on the network. Unusable keys (encryption keys, RSA below 2048 bits, points off the curve) are skipped. Provisioning waits up to 3 s for the first fetch so a fresh start does not reject every token. Shared HMAC secrets come from an environment variable (at least 32 bytes), never from the configuration.
6. **Identity for rate limits.** The module stores only verified claims (`Decision.SetClaims`) and the verified client-certificate subject. `jwt:<claim>`, `api_key:<header>` and `mtls_subject` keys use them; when the identity is absent the key falls back to the client address so an anonymous client cannot hide in someone else's bucket. API-key values are hashed before use. For this reason `sherlock_api` runs before `sherlock_ratelimit` (request-pipeline.md).
7. **Mutual TLS.** CA bundles are uploaded certificates only (CA:TRUE, not expired, at most 20; a private key in the upload is refused) and are referenced by id like certificates (ADR-0016). The site's TLS policy gets `client_authentication` with `verify_if_given` and the CA as inline base64 DER, so the handshake verifies any certificate offered but does not lock out clients on other paths; `sherlock_api` refuses requests on `mtls.required_paths` without a verified chain. Because the policy is per listener name, the CA comes from the site-level policy.
8. **Mode.** In `detect` mode every block action becomes a finding, like the WAF; `off` skips the module. An `api.document_missing` notice is raised, and requests pass, if a referenced document is not loaded (the reference checker prevents this in normal operation).

## Consequences

- No new direct dependency; the verifier is about 300 lines to review (`internal/dataplane/api/jwt.go`, `jwks.go`) and has a fuzz target in the nightly workflow.
- Key rotation, JWKS outages and document replacement need no reload.
- A deployment that needs EdDSA or PS keys delivered as JWK works; JWE (encrypted tokens) and detached JWS are out of scope.
- `verify_if_given` means a client presenting an invalid certificate fails the handshake even on paths that do not require one. That is the safe reading and is documented.
