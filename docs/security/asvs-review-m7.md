# Internal ASVS 5.0 Level 2 review of the control plane (M7-T9)

- Date: 2026-10-29
- Reviewer: AI agent (Claude), for the owner. This is an **internal, self-review** of the code the same project wrote. It is a gate input, not an independent assessment; an external review is still advisable before general availability.
- Standard: OWASP ASVS 5.0 (chapters V1 to V17), target level 2.
- Scope: the control plane at the repository state of this change: `internal/controlplane/api` (server, middleware, handlers), `internal/controlplane/auth`, `internal/controlplane/tlscert`, `internal/server` (listener, jobs), `internal/audit`, `internal/secrets` (usage only), the new `internal/updater`, `internal/ops` backup/restore, `pkg/cli` commands that touch state, `api/openapi.yaml`, `deploy/systemd/sherlock.service`, `deploy/install/install.sh`. Not in scope: the data plane (`internal/dataplane/*`, covered by go-ftw and its own review), the dashboard (`web/`, another owner), Enterprise extensions.
- Method: read the code paths for each chapter, ran and extended the existing tests, and exercised suspect paths with throw-away tests. Requirement IDs are cited at chapter and topic level, not verbatim, because the full ASVS 5.0 text was not re-read line by line against each item; a reviewer should map the findings to exact requirement numbers when this is signed off.

## Result in one paragraph

No Critical or High findings. Four Medium and several Low findings were fixed in this change (listed first); the remaining items are ticketed with severity below. Phase 2 acceptance criterion 6 (no open critical or high findings) is met. No Medium item remains open. S-01 (self-service password change) is fixed as described in its row below. S-02 (request validation against the OpenAPI schema) and S-14 (content-type enforcement) are fixed as described in the rows below.

## Fixed in this change

| F-01 | Medium | V15 (secure coding, SSRF), V13 | `POST /system/upstream/test` dialled any `host:port` with a plain HTTP client. A `config:write` principal (a scoped token is enough) could probe the cloud metadata address `169.254.169.254` or any link-local address and learn reachability and the HTTP status, contradicting the project SSRF rule. | The probe now uses the `netx` client with `AllowPrivate: true` (private upstreams stay testable) which always refuses link-local, multicast and unspecified addresses, checked on the dialled address (DNS rebinding safe). Result class `blocked`. Test: `TestTestUpstreamRefusesMetadataAndLinkLocal`. |
| F-02 | Medium | V14 (data protection), V8 | The site password-gate hash (`password_hash`) was returned in `GET /config`, `/defaults`, `/sites`, `/sites/{site}`, endpoints and `/config/versions/{id}` to every reader, including viewer-role users and `read`-scoped tokens. A hash is offline-crackable. | Redacted to `<redacted>` in all those responses for every caller. On write, `<redacted>` or an omitted field keeps the stored hash, matched by site and endpoint id; a placeholder with nothing stored is cleared so validation fails; the live configuration is never mutated. Documented in `docs/user/control-plane.md`. Tests: `internal/config/redact_test.go`, `TestPasswordHashIsRedactedAndPreserved`. |

Administrators could not reset a user's password through the API, a broken security control rather than a leak. No test covered it. | Detail key renamed `credentials_changed`. Test: `TestAdminCanResetAPasswordThroughTheAPI` (also asserts sessions end and the password never reaches the audit log). |
| F-04 | Low | V6 (password security) | The password policy was length only (12 to 1024). | Common and predictable passwords of 12+ characters (a short list, repeated characters, straight runs) are refused. This is a floor: see S-06 for the full corpus check. |
| F-05 | Low | V12 (secure communication), V13 | `install.sh` fetched with `curl` defaults (any protocol, any TLS version) and matched the package name in `checksums.txt` as a regular expression. | `--proto =https --tlsv1.2` on every download; exact-field match with `awk`. |

## Open findings (ticketed)

Severity is the reviewer's estimate of risk in the intended deployment (a single node, control plane on loopback or a private network, reached by a small trusted admin group).

| ID | Severity | ASVS area | Finding | Recommendation |
| --- | --- | --- | --- | --- |
| S-01 | Medium | V6 (authentication lifecycle) | **Fixed.** There was no self-service password change. Users depended on an administrator (`PATCH /users/{id}`) or the CLI. A user who suspected compromise could not rotate their own password, and an admin who reset it learned the new one. | **Fixed:** `POST /auth/password` takes `current_password` and `new_password` from a full browser session only (no tokens, no pre-MFA sessions). The current password is verified in constant time and every attempt counts against a per-user limit of 5 a minute, the same bound as login, without locking the account. A wrong current password is a 422 on `/current_password`, not a 401, so the dashboard does not treat it as an expired session. The new password must pass the policy and differ from the current one. The change, the other sessions ending and the audit row (`user.password_changed`, with the number of sessions revoked, never a password) happen in one transaction. Failures are audited as `user.password_change_failed` with a reason only. The caller stays signed in. |
| S-02 | Medium | V2 (validation), V4 (API) | **Fixed.** Request bodies and parameters were not validated against the OpenAPI schema constraints (`minLength`, `maxLength`, `pattern`, enum, `minimum`, `maximum`, `format`) at runtime; handlers hand-validated and only configuration bodies were strictly decoded. | **Fixed:** every control-plane request is validated against `api/openapi.yaml` in the guard, after authentication and authorisation and before strict decoding. Violations return 422 with `errors[{path,code,message}]` using JSON pointers; malformed JSON, missing bodies and bodies over 4 MiB return 400. The data plane uses the same validator (`internal/oapi`). Hand validation remains as a backstop. Tests: spec-driven table in `internal/controlplane/api/validate_test.go`; commit reference to be added by the owner. |
| S-03 | Low | V7 (sessions), V8 | **Fixed.** Users could not list or revoke their own sessions, and the number of concurrent sessions was not limited. Password and role changes and MFA reset did end all sessions, and idle (30 min) and absolute (12 h) limits were enforced. | **Fixed:** `GET /auth/sessions` lists the caller's full browser sessions, and `DELETE /auth/sessions/{id}` ends one of the caller's other sessions. An id belonging to another user, or to no session, is a 404, so the response does not reveal which ids exist. The current session cannot be revoked here (409; sign-out ends it). Session ids are the hex SHA-256 of the cookie value, which carries 256 bits of randomness, so an id cannot be turned back into a cookie. Each user has at most 5 concurrent full sessions; creating a sixth evicts the oldest and is audited as `auth.session_evicted`. |
| S-04 | Low | V6, V16 | Failed API-token authentication is not audited or throttled. Secrets are 160-bit random and compared in constant time, so guessing is infeasible; the gap is detection (no log of a spraying attempt) and flooding the store with lookups. | **Fixed:** a client address with more than 10 failed token presentations in a minute is refused with 429 before the lookup, and failures are audited as `auth.token_failed` at most once a minute per address with a count (no token id, secret or token). Residual: a shared address (NAT) can be blocked for up to a minute by one client's failures. |
| S-05 | Low | V6, V9 (tokens) | Tokens may have no expiry and no maximum lifetime or count per user. An `admin`-scoped token can also trigger `POST /system/update/apply` (it can only stage a validly signed, newer release). | **Fixed:** maximum lifetime 365 days by default (`SHERLOCK_API_TOKEN_MAX_DAYS`, `0` for none); an omitted expiry becomes the maximum and a longer one is a 422 on `/expires_at`; 50 tokens per account (409); an expires-soon badge within 14 days; `POST /system/update/apply` refused for API tokens (403). The CLI path applies the same maximum. Residual: the per-account count is serialised in-process, so a multi-node deployment on PostgreSQL could exceed 50 by one under a race (single node is the supported model). |
| S-06 | Low | V6 (password security) | Passwords are not checked against a top-3000 or breach corpus, only against the short list from F-04. | **Fixed:** an embedded corpus of 29,919 breached passwords of 12+ characters (SecLists `Pwdb_top-1000000`, MIT; `internal/controlplane/auth/data/common-passwords.txt`, licence in NOTICE), matched after lower-casing, removing trailing digits and symbols and decoding common leetspeak. The top-10k list yields only 10 entries of 12+ characters, so it was not sufficient alone. Residual: an offline list is weaker than a live k-anonymity check against a breach service, which would need a network call the design forbids on the request path. |
| S-07 | Low | V6 (anti-automation) | Login lockout and the per-username limiter are keyed on the username, so an attacker can lock out a known administrator (5 attempts per minute, then 1 to 15 minute locks) without knowing the password. This is the usual trade-off against guessing; the CLI can always reset. | **Fixed (limiter only):** the limiter is keyed on (IP, username) at 5 a minute, and the per-username ceiling across all clients is 20 a minute (was 5), so a distributed attacker cannot lock out an administrator with a handful of attempts; each new account lock is audited once as `auth.account_locked`. **Open residual, owner decision:** the account lock itself is still stored per account (`LockedUntil`), so a remote attacker who keeps failing passwords can keep the account locked. The recommendation as written does not remove that; see Residuals below. |
| S-08 | Low | V6 (anti-automation) | There is no general API rate limit; only login, the setup token and the update-status cache are limited. The Hasher semaphore bounds concurrent argon2 runs. | **Fixed:** `guard()` counts after authentication: 300 requests a minute per signed-in user or token, and 120 a minute per client address for anonymous public operations, using `internal/policy/ratelimit`; refusals are 429 with `Retry-After` and counted in `sherlock_api_throttled_total`. Unauthenticated requests to protected operations are refused before any count. The dashboard polls at most every 5 s. Residual: counters are per process. |
| S-09 | Low | V6, V15 | `POST /setup/admin` hashes the submitted password (argon2id, 64 MiB) before the setup token is checked, so an unauthenticated caller can burn up to four concurrent hashes while setup is open. Bounded by the Hasher semaphore and only possible until the first admin exists. | **Fixed:** the token is verified (constant time, throttled) before the hash; the token is consumed only after the administrator row commits, so a request that fails later leaves it usable. Test: a wrong or throttled token causes no argon2 run (`TestSetupRefusesBadTokenBeforeHashing`). |
| S-10 | Low | V16 (logging) | `docs/security/secure-development.md` names a redacting slog handler in `internal/logging` that does not exist. No reviewed code path logs a credential, token, cookie or TOTP code (errors are logged with request ids, details never reach responses), but nothing enforces it. | Implement the handler or correct the document; add a test that logs a secret-shaped attribute. |
| S-11 | Low | V14 | A plain (unencrypted) backup contains Caddy's ACME account and certificate keys and the control plane's TLS private key in clear. Backups are 0600 in a 0700 directory, uploaded-certificate keys are excluded (`certs/`), the node key is never included without encryption, and `SHERLOCK_BACKUP_PASSPHRASE_FILE` encrypts scheduled backups, but encryption is opt-in. | Make encryption the default when a passphrase file exists (done) and document prominently (done); consider an `--encrypt` default in a later major version. |
| S-12 | Low | V13, V11 (supply chain) | The release signing key has no revocation list in the binary, no written rollover procedure, and a source build ships with the `UNSET` placeholder key (updates disabled, fail closed). See ADR-0017 consequences. | Write the key-rollover runbook and generate and commit the real public key before the first release (release blocker for acceptance criteria 2 and 3). |
| S-13 | Low | V16 (audit) | The audit hash chain is not anchored off the box: a database writer can rewrite the newest entries (documented limit in `internal/audit`). Checkpoints are logged periodically. | Ship checkpoints to an external sink (Enterprise signed checkpoints are planned). |
| S-14 | Info | V3, V4 | **Fixed.** JSON endpoints did not require `Content-Type: application/json`. | **Fixed:** an operation with a body refuses a `Content-Type` its document does not declare with 415 (merge-patch operations accept only `application/merge-patch+json`). Tests: `TestMediaTypeAndBodyRules`; commit reference to be added by the owner. |

## Residuals and owner decisions (this change)

- **S-07 account lock (owner decision).** The per-account lock (`LockedUntil`, set after five consecutive wrong passwords from anywhere) still lets a remote attacker keep a known administrator locked out, one attempt per lock cycle. Options: keep the lock and accept it (the CLI reset is always available), exempt the lock from remote failures, or lock only per (IP, username) in the store. **Resolved by configuration:** `SHERLOCK_LOGIN_LOCK_AFTER` and `SHERLOCK_LOGIN_LOCK_MAX_MINUTES` tune the lock, and `SHERLOCK_LOGIN_LOCK_AFTER=0` turns it off (the per-address and per-username rate limits still bound guessing). The default is unchanged.
- **B2 concurrent sign-ins (PostgreSQL).** Two sign-ins racing on PostgreSQL can both create a session before the 5-session eviction runs, so a user may briefly hold more than five full sessions. The next sign-in trims them back. SQLite serialises writers and does not show this. **Fixed (M11):** the cap check runs under a per-user row lock (`store.Tx.LockUser`), covered by a conformance test that fails on PostgreSQL without the lock.
- **S-05 token count.** The 50-token check was serialised by an in-process mutex only. **Fixed (M11):** it now runs under the same per-user row lock, so it holds across processes and nodes.
- **MFA on password change.** **Fixed (M11):** `POST /auth/password` needs a current TOTP code when MFA is enrolled (single-use, replay-protected, audited).
- **S-04 and S-08 counters** are per process (with several nodes the effective limit is the configured value times the node count; shared counters are M12) and keyed on the address the request came from; behind a reverse proxy every client shares the proxy's address unless the proxy is trusted, which this change does not add.
- **Audit rows.** Pre-login audit rows (`auth.login_failed` for unknown users, `auth.login_throttled`) were previously refused by the audit table's actor check and never stored. They are stored now as the `system` actor `anonymous`. Historic gaps in an existing database cannot be recovered.
